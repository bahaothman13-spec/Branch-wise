# تدقيق جاهزية تكامل قاعدة البيانات — BE-03 الجزء 2

**حالة التدقيق:** اكتمل بمراجعة الملفات المحلية. قاعدة البيانات غير مثبتة التكامل.

## حالة التنفيذ الحالية

- `backend/db.py` يفتح اتصالًا مباشرًا باستخدام `mysql.connector`. يقرأ `DB_HOST` و`DB_USER` و`DB_PASSWORD` و`DB_NAME` من متغيرات البيئة أو `backend/.env`، ويستخدم `DB_PORT` أو القيمة الافتراضية `3306`. عند غياب الإعدادات أو فشل الاتصال أو عدم صلاحية المنفذ، يسجل تحذيرًا عامًا ويعيد `None`.
- لا ينفذ `db.py` استعلامات أو معاملات، ولا يعرّف جلسات أو نماذج ORM أو إدارة لدورة حياة الاتصال. كما أن إنشاء تطبيق Flask لا يفتح اتصالًا تلقائيًا.
- لا يوجد في مسارات التطبيق الحالية استدعاء لطبقة اتصال قاعدة البيانات أو عملية قراءة/كتابة موثقة. وجود دالة فتح الاتصال وحده لا يعني أن قاعدة البيانات مدمجة.
- `backend/security.py` يوفر تجزئة كلمة المرور والتحقق منها باستخدام Werkzeug. وتوجد قواعد صلاحيات وتهيئة أول فرع في ملفات مستقلة، لكنها لا تصادق المستخدم ولا تقرأ أو تكتب قاعدة بيانات.
- `backend/.env.example` يحتوي أسماء الإعدادات وقيمًا إرشادية فقط. لا تتوفر ضمن ملفات Backend الظاهرة إعدادات محلية موثقة لاتصال حقيقي.

## المسارات وواجهات API

المسارات المسجلة في `backend/app.py` هي:

| الطريقة والمسار | السلوك الحالي |
| --- | --- |
| `GET /api/health` | يعمل ويعيد `200` مع `{"status":"ok"}`. |
| `POST /api/auth/register` | يتحقق من المدخلات؛ غير الصالح يعيد `400`، والصالح يعيد `501`. لا ينشئ Owner أو نشاطًا تجاريًا. |
| `POST /api/auth/login` | يتحقق من المدخلات؛ غير الصالح يعيد `400`، والصالح يعيد `501`. لا يتحقق من بيانات اعتماد. |
| `POST /api/auth/logout` | يعيد `501`؛ إدارة الجلسات غير مطبقة. |
| `GET /api/branches` | يعيد `501`. |
| `POST /api/branches` | يتحقق من المدخلات؛ الصالح يعيد `501`. |
| `GET /api/branches/<branch_id>` | معرّف غير صالح يعيد `400`؛ المعرّف الصالح يعيد `501`. |
| `PATCH /api/branches/<branch_id>` | طلب غير صالح يعيد `400`؛ الطلب الصالح يعيد `501`. |
| `PATCH /api/branches/<branch_id>/deactivate` | معرّف غير صالح يعيد `400`؛ المعرّف الصالح يعيد `501`. |
| `POST /api/users` | يتحقق من المدخلات؛ الصالح يعيد `501`. |
| `PATCH /api/users/<user_id>/status` | طلب غير صالح يعيد `400`؛ الطلب الصالح يعيد `501`. |
| `PATCH /api/users/me/password` | يتحقق من المدخلات؛ الصالح يعيد `501`. |

بذلك، واجهة الصحة فقط تنفذ عملية API مكتملة. بعض المسارات الأخرى تنفذ التحقق من المدخلات، لكن عملياتها التجارية غير مكتملة وتعيد `501` للطلبات الصحيحة. لا تطبق المسارات الحالية مصادقة أو حماية فعلية. لا توجد مسارات API مسجلة للمنتجات أو المتغيرات أو المخزون؛ ملفات قواعد المنتجات والمتغيرات والحركة المخزنية هي منطق مستقل وليست واجهات API أو عمليات قاعدة بيانات.

## تغطية الاختبارات ذات الصلة

- يحتوي `backend/tests/test_db.py` على خمسة اختبارات وحدات لاتصال وهمي: قراءة إعدادات `.env` وتمريرها للموصل، عدم الاتصال عند نقص الإعدادات، معالجة خطأ الموصل دون تسجيل السر، رفض منفذ غير صالح، وعدم اتصال التطبيق عند إنشائه.
- هذه الاختبارات لا تتصل بخادم MySQL، ولا تنفذ استعلامًا أو معاملة، ولا تتحقق من وجود مخطط أو جداول.
- يغطي `backend/tests/test_api.py` استجابة الصحة والتحقق من المدخلات وحالات `400` و`501` للمسارات الحالية. وهو يستخدم Flask test client دون قاعدة بيانات.
- توجد اختبارات لقواعد كلمات المرور والصلاحيات والتهيئة والمنتجات والمتغيرات والمخزون، لكنها تختبر قواعد مستقلة عن قاعدة البيانات.
- لا توجد اختبارات تكامل مع MySQL في الملفات المفحوصة. لم تُشغّل الاختبارات أثناء هذا التدقيق.

## أصول قاعدة البيانات المتاحة

- المتاح هو `backend/.env.example`، وكود فتح الاتصال في `backend/db.py`، و`backend/requirements.txt`.
- لا توجد ملفات DDL أو SQL لإنشاء المخطط، ولا ملفات ترحيل، ولا بيانات بذر/تهيئة، ولا وثائق محلية لتعريف قاعدة البيانات. لم تظهر هذه الأصول في الملفات المتتبعة أو مراجع Git المحلية التي فُحصت.
- `API_CONTRACT.md` و`backend/ROLE_PERMISSIONS.md` يصفان سلوك API والصلاحيات، ولا يحددان مخطط قاعدة البيانات.
- تظهر `catalog_codes` في قواعد المنتجات والمتغيرات كمدخلات بيانات يمررها المستدعي (سجل في الذاكرة). هذا لا يثبت وجود جدول فعلي أو أعمدته.

### مرجع الجداول المعتمد والتعريفات المتاحة

بحسب وصف المهمة، يحدد أحدث مرجع معتمد لـ BranchWise **33 جدول أعمال، ومنها `catalog_codes`**. ملف ذلك المرجع غير موجود محليًا، لذلك لا يمكن مراجعة القائمة الكاملة أو استخدام مخطط أقدم بدلًا منه. اسم `catalog_codes` هنا معلوم من وصف المهمة ومن قواعد العمل، لكن تعريف الجدول غير متاح محليًا.

| المجال المطلوب | هل تتوفر تعريفات جدول/أعمدة محلية؟ |
| --- | --- |
| التسجيل وتسجيل الدخول | لا توجد خريطة محلية للعملية إلى الجداول أو أعمدة التحقق والاعتمادات. |
| المستخدمون | لا يوجد تعريف جدول أو أعمدة أو قيود. |
| الفروع | لا يوجد تعريف جدول أو أعمدة أو قيود. |
| المنتجات | لا يوجد تعريف جدول أو أعمدة أو قيود. |
| المتغيرات | لا يوجد تعريف جدول أو أعمدة أو قيود. |
| `branch_inventory` | لا يوجد تعريف جدول أو أعمدة أو قيود. |
| `catalog_codes` | الاسم مذكور، لكن لا يوجد DDL أو تعريف أعمدة/قيود محلي. |

لا يجوز استنتاج أسماء أعمدة أو علاقات أو مفاتيح أو قيود لهذه الكيانات من أسماء حقول API أو dataclasses أو قواعد الأعمال.

## الاعتماديات والفرق عن متطلبات ORM

- يعتمد التنفيذ الحالي على `mysql-connector-python==26.10.0` و`python-dotenv==1.2.4`، مع Flask. لا تظهر `SQLAlchemy` في `backend/requirements.txt`، ولا تظهر نماذج أو محرك أو جلسات SQLAlchemy في التنفيذ.
- يشير متطلب Backend المعتمد المذكور في وصف المهمة إلى SQLAlchemy/ORM. إذن التطبيق الحالي يستخدم موصل MySQL مباشرًا بدل طبقة ORM، ويفتقد اعتماد SQLAlchemy وإعداد ORM المطلوبين لذلك المسار.
- لا توجد ملفات ترحيل أو أداة ترحيل أو نماذج ORM. لا يمكن الجزم من المستند غير المتاح إن كانت أداة بعينها مثل Alembic مطلوبة؛ يلزم الرجوع إلى المستند قبل اعتماد أداة ترحيل.
- لا تغيّر طريقة الاتصال ضمن هذا التدقيق. يلزم قرار الفريق بشأن الالتزام بـ SQLAlchemy/ORM مقابل التنفيذ المباشر الحالي قبل بناء طبقة استمرارية جديدة؛ لا ينبغي افتراض التوافق أو إجراء التحويل منفردًا.

## العوائق الدقيقة

1. غياب أحدث مرجع قاعدة البيانات المعتمد ذي الجداول الـ33، بما فيه تعريف `catalog_codes` الكامل.
2. عدم توفر DDL أو ترحيلات أو بذر أو أي مصدر محلي موثوق لأسماء الجداول والأعمدة والعلاقات والقيود.
3. عدم توفر تعريفات الجداول والأعمدة المطلوبة للمستخدمين والفروع والمنتجات والمتغيرات و`branch_inventory`، أو خريطة تسجيل Owner/تسجيل الدخول إلى المخطط.
4. عدم حسم قرار الفريق بشأن متطلب SQLAlchemy/ORM مقابل `mysql-connector-python` المباشر الحالي؛ كما أن SQLAlchemy والنماذج والجلسات غير موجودة في الاعتماديات والتنفيذ الحاليين.
5. لا يوجد دليل على اتصال ناجح بخادم MySQL حقيقي أو تنفيذ عملية قراءة/كتابة ذات صلة. اختبارات الاتصال الحالية تستخدم mocks فقط، وملف البيئة المتاح مثال غير تشغيلي.
6. المصادقة والجلسات والهوية الموثوقة غير مطبقة في المسارات. يجب حسم آلية الجلسة/الرمز وربطها بالمستخدم والنشاط والصلاحيات قبل حماية المسارات.

## ترتيب التكامل المقترح

1. **إغلاق بوابة المرجع والقرار التقني:** توفير نسخة المرجع المعتمد ذي الجداول الـ33، والتحقق من تعريفات الجداول المطلوبة، وحسم ORM والموصل وأداة الترحيل مع الفريق. لا تُنشأ جداول أو أعمدة بالاستنتاج.
2. **الاتصال بقاعدة البيانات:** إعداد بيئة اختبار MySQL معتمدة وإعداداتها خارج المستودع، ثم تنفيذ اختبار اتصال حقيقي عبر طبقة الاتصال التي يقررها الفريق. تحقق من دورة إغلاق الاتصال والأخطاء دون كشف أسرار. سجّل نتيجة عملية اتصال فعلية قبل وصف الاتصال بأنه متحقق.
3. **تطبيق المخطط المعتمد:** استخدام ملفات المخطط/الترحيل الرسمية بعد استلامها، والتحقق من الجداول والأعمدة والقيود والفهارس المتوقعة، ثم إضافة بيانات البذر المعتمدة فقط إن وجدت.
4. **أساس المصادقة:** إعادة استخدام تجزئة كلمات المرور الموجودة، وتنفيذ التحقق من بيانات الدخول وبناء هوية موثوقة من بيانات مخزنة. احسم آلية الجلسة أو الرمز وتغطية الاختبار قبل حماية المسارات.
5. **تسجيل Owner:** تنفيذ إنشاء Owner والنشاط التجاري وفق المخطط المعتمد وبمعاملة ذرية، مع التحقق من التفرد وتخزين تجزئة كلمة المرور فقط.
6. **إنشاء أول فرع:** حماية العملية بهوية Owner موثقة، واستخدام معرّف النشاط التجاري من الهوية الموثوقة، والتحقق من شرط أول فرع والتفرد ضمن النشاط، ثم الحفظ ذريًا.
7. **المسارات المحمية:** ربط واجهات الفروع والمستخدمين القائمة بالمصادقة والصلاحيات ونطاق النشاط/الفرع. بعد توفر المخطط، ربط واجهات المنتجات والمتغيرات والمخزون بقواعد العمل الموجودة، وتحميل `catalog_codes` من مصدره المعتمد. وسّع التكامل لبقية النطاق بحسب العقود المعتمدة.
8. **التحقق النهائي:** إضافة/تشغيل اختبارات تكامل على MySQL حقيقي أو بيئة اختبار معتمدة، بما يشمل الاتصال والقراءة والكتابة والمعاملات والتفرد ونطاق النشاط والصلاحيات. لا يُعلن اكتمال التكامل قبل نجاح الاتصال والعمليات ذات الصلة.

## ما يمكن تنفيذه فورًا

- يمكن إعادة استخدام قواعد التحقق وكلمات المرور والصلاحيات والتهيئة وقواعد المنتجات والمتغيرات والمخزون الموجودة، مع إبقائها مستقلة عن مخطط غير مؤكد.
- يمكن تجهيز بيئة اختبار اتصال حقيقي واختبارها بعد توفير إعدادات MySQL المعتمدة وحسم طبقة الاتصال. هذا تحقق اتصال فقط، ولا يثبت CRUD أو تكامل الأعمال.
- يمكن متابعة قرار الفريق ومراجعة المرجع المعتمد وتحديد حالات التكامل والاختبارات المطلوبة. أما كتابة عمليات التخزين أو تنفيذ التسجيل أو تسجيل الدخول أو إنشاء أول فرع فلا يمكن إنجازها بأمان قبل إزالة عوائق المخطط وقرار ORM والمصادقة.

**النتيجة:** لم يثبت اتصال MySQL حقيقي ولا أي عملية قاعدة بيانات ناجحة في هذا التدقيق؛ لذلك لا تُعد قاعدة البيانات مدمجة.
