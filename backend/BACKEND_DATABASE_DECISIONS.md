# قرارات Backend–Database وحالتها بعد معالجة توافق Backend

**التاريخ:** 7 نوفمبر 2026
**الفرع:** `backend-dev1`

تمت مراجعة `User story.docx` و`backend.docx` و`database final(1).docx` مع قواعد Backend الحالية. هذا التحديث يميز بين قرارات Backend القابلة للتنفيذ وبين التعارضات التي لا تزال تحتاج اعتماد Database/الفريق. نُفذت التعديلات على قواعد المال الخالصة، وضُبط توليد كلمات المرور صراحةً على Werkzeug scrypt، وأُبقي التحقق متوافقًا مع صيغ Werkzeug المحفوظة. لم يتغير مخطط قاعدة البيانات أو migrations أو سلوك التحويل أو وحدات Backend Developer 2، ولم يُجرَ commit أو push.

## قرارات Backend الموثقة والمنفذة

| المجال | القرار والحالة |
|---|---|
| المال في قواعد Backend الخالصة | Backend D-05 يحدد JOD، والسعر/التكلفة `DECIMAL(14,3)`، وإجماليات البيع `DECIMAL(16,3)`. حُدثت قواعد المنتج والبيع وسجل البيع لتطبيق هذه الحدود بدقة Decimal؛ لا يحدث تقريب أو تغيير في الأرقام الواقعة ضمن الحدود السابقة. |
| تجزئة كلمة المرور في تنفيذ Backend الحالي | طلب المهمة الحالية يحدد Werkzeug scrypt صراحةً، لذلك أصبح توليد الهاش يستخدم `method="scrypt"`. بقي `check_password_hash` دون تغيير، ويقرأ الهاشات ذاتية الوصف التي سبق أن أنشأها Werkzeug، بما فيها scrypt. |
| قواعد النقل الأساسية | BW-10 يقرر أن Pending بلا أثر مخزني، والإرسال يعيد فحص المتاح ويخصم المصدر مرة واحدة، والوجهة لا تضاف لها إلا الكمية المستلمة فعليًا، مع منع التكرار. لم يتغير كود النقل في هذه المهمة. |
| حفظ الكمية | D-04 يثبت معادلة الحفظ: `dispatched = received_good + returned_to_source + written_off + unresolved`. الذرية وعدم تكرار القيود جزء من الاتفاق؛ شرط حالة رأس التحويل ما زال متعارضًا أدناه. |
| أسماء Backend داخل قواعد الأعمال | الحقول الحالية تستخدم `snake_case` وأسماء المجال مثل `product_code` و`total_amount` و`unit_price_snapshot`. بقيت أسماء DTO كما هي؛ تحويلها إلى أسماء أعمدة DB مثل `variant_code` و`line_total` و`total` يحتاج اعتماد خريطة المجال إلى المخطط قبل تثبيت طبقة ORM/API. |

## مسائل تنتظر اعتماد Database أو الفريق

| القرار | التعارض الحالي | المطلوب |
|---|---|---|
| دقة المال في التخزين | Backend D-05 يحدد JOD و3 منازل عشرية (`DECIMAL(14,3)` للسعر و`DECIMAL(16,3)` للإجمالي)، بينما Database DEC-02 يحدد المال `DECIMAL(14,2)` ولا يثبت JOD. | اعتماد عقد واحد من Database والفريق قبل أي نموذج ORM أو migration. قواعد Backend الخالصة الحالية تتبع D-05 فقط؛ لم يتغير المخطط. |
| خوارزمية كلمة المرور | المهمة الحالية طلبت توليد scrypt صراحةً. Database يحدد Argon2id/bcrypt في `password_hash VARCHAR(255)`. | اعتماد scrypt تعاقديًا أو تحديد الخوارزمية البديلة قبل ربط الهاشات بتخزين دائم. يبقى التحقق متوافقًا مع الهاشات الموجودة. |
| نطاق الأكواد | Backend D-01 يجعل `product_code` وSKU في نطاقي تفرد مستقلين؛ Database DEC-04 يطلب سجلًا مشتركًا يمنع التصادم بين المنتج والمتغير. | قرار Database/الفريق قبل اعتماد القيود أو تغيير سلوك التحقق. |
| أسماء DTO والأعمدة | Backend يستخدم أسماء مجال مثل `code` و`unit_price_snapshot` و`line_subtotal` و`total_amount`؛ ملف DB يسمي الأعمدة `variant_code` و`unit_price` و`line_total` و`subtotal`/`total`. | اعتماد خريطة ORM/API. لم تُغيّر أسماء DTO أو مخطط DB في هذه المهمة. |
| حالة التحويل بعد استلام جزئي | BW-10/243 وDB PROC-12 يضعان الرأس `COMPLETED` بعد تأكيد الاستلام مع بقاء النقص في عهدة `IN_TRANSIT`؛ Backend D-04 يقول إن الإكمال ينتظر `unresolved=0`. | لا تغيّر سلوك التحويل إلى أن يعتمد الفريق رسميًا تعديل العقد المتعارض. لم يتغير كود أو اختبار النقل. |
| `CANCELLED` للتحويل | Database DEC-06 يضيف الحالة؛ قائمة حالات BW-10/240 لا تتضمنها رغم اشتراط معالجة الإلغاء في BW-10/245. | توضيح قائمة الحالات/اعتماد اسمها قبل تعديل enum أو قواعد الانتقال. |
| نسخة المخطط وعدد الجداول | `backend.docx` يعلن مخططًا معتمدًا من 32 جدولًا؛ `database final(1).docx` يعلن 36 جدولًا إلزاميًا، مع اختلاف حول إلزامية `ai_decision_outcomes`. | تثبيت نسخة المخطط والعدد من مالك Database والفريق. |
| `idempotency_requests` | BE-52 يطلب سلوك idempotency والجدول؛ قائمة Database ذات 36 جدولًا لا تتضمنه ولا تحدد DDL/مدة الاحتفاظ بالنتيجة. | اعتماد DDL أو بديل يغطي بصمة الحمولة والنتيجة المحفوظة والتزامن، ثم تحديث عدد الجداول. |
| بصمة CSRF | اقتراح `auth_sessions.csrf_token_hash BINARY(32)` غير موجود في تعريف جلسة Database المراجع. | اعتماد إضافة الحقل من مالك Database قبل استخدامه في مخطط دائم. |

## أثر عدد الجداول

- العدد المذكور في `database final(1).docx` هو 36 جدولًا إلزاميًا، ولا يتضمن `idempotency_requests`.
- إذا اعتُمد جدول idempotency إلزاميًا فوق نسخة DB ذات 36 جدولًا، يصبح العدد 37؛ وإذا ثبت أن نسخة Backend ذات 32 جدولًا هي المرجع، يصبح 33. لا يثبت العدد النهائي قبل توحيد النسخة.
- لا يُحسب الجدول الاختياري ضمن عدد الجداول الإلزامية.

## نطاق التعديل المنجز

- ضبط Werkzeug على scrypt صراحةً مع الحفاظ على التحقق المرن من الهاشات المخزنة.
- مواءمة حدود أسعار وتكاليف المنتجات وأسعار البيع مع D-05: ثلاث منازل و`DECIMAL(14,3)`؛ ومواءمة إجماليات بنود البيع وإجمالي العملية مع `DECIMAL(16,3)`.
- تحديث اختبارات الحدود والدقة واختبارات التحقق من الهاش.
- لم تتغير قاعدة البيانات أو migrations أو انتقالات التحويل أو وحدات Backend Developer 2.
- شُغلت مجموعة pytest كاملة بعد التعديل؛ تفاصيل النتيجة في سجل التوافق.
