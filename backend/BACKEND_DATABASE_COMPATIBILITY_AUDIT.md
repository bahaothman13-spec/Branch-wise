# تدقيق توافق Backend مع مخطط قاعدة البيانات المعتمد

**التاريخ:** 6 نوفمبر 2026  
**مرجع قاعدة البيانات المستخدم:** الملف المحدد في جذر المشروع database final(1).docx، بعنوان *BranchWise — Database Implementation Master Plan*، الإصدار 1.0.  
**النطاق:** مطابقة قرارات Backend الموثقة وقواعده الحالية مع المخطط المحدد. عُدّل هذا التقرير فقط؛ لم تُعدّل الشيفرة أو الاختبارات أو الاعتماديات أو الترحيلات، ولم يُجرَ commit أو push. لم تُشغّل الاختبارات ولم يُختبر اتصال MySQL حقيقي.

## الخلاصة

استُخدم database final(1).docx نفسه مرجعًا للمقارنة؛ لذلك أُزيلت خلاصة التدقيق السابق التي قالت إن الملف غير متاح واعتمدت ملفًا مختلف الاسم. يثبت الفحص وجود خلافات عقدية بين مرجع Backend المجمد ومرجع قاعدة البيانات، إضافةً إلى فجوات تنفيذية داخل القواعد الحالية. لا يوجد في المستودع مخطط SQL أو migrations أو طبقة تخزين دائمة تتيح إثبات توافق تشغيل فعلي.

أهم ما يتطلب حسمًا قبل بناء التخزين الدائم: عدد الجداول وقائمة المطابقة، مساحة أكواد المنتجات والمتغيرات، دقة المال، تمثيل أرصدة المخزون، حالة التحويل مع فرق مفتوح، عقد idempotency، حالة WAIT لتوصيات AI، وحقل بصمة CSRF. كما ينبغي معالجة خوارزمية تجزئة كلمات المرور قبل تخزين حسابات جديدة.

## 1. المراجع وحدود الإثبات

- يعرّف ملف قاعدة البيانات قرارات DEC-01 إلى DEC-15 وقاموسًا مرقمًا حتى 36، ثم ثلاثة جداول إضافية اختيارية: ai_assistant_queries وcsv_import_batches وcsv_import_rows.
- ملف Backend الخارجي backend.docx يصف مخططًا من 32 جدولًا ويجعل قرارات D-01 إلى D-07 مرجعًا لعقود Backend. لم تتوفر قائمة الجداول الـ32 نفسها ضمن ملفات المشروع، لذلك أمكن تأكيد اختلاف العدد والأسماء المعروفة، لكن لا يمكن إعداد مطابقة كاملة لكل جدول.
- backend/INTEGRATION_READINESS.md لا يزال يصف 33 جدولًا وcatalog_codes وbranch_inventory، ويقول إن المرجع المعتمد غير متاح. هذه المعلومات أصبحت قديمة بالنسبة إلى الملف المحدد.
- لا يحتوي المستودع على DDL أو ملفات migrations أو نماذج ORM أو مستودعات تخزين دائمة. الملاحظات أدناه تميز بين تعارض الوثائق، وسلوك قواعد Python النقية، وما لم يُنفذ بعد؛ ولا تدعي نجاح تكامل قاعدة بيانات.

## 2. التعارضات والفجوات المثبتة

### F-01 — عدد الجداول وقائمة المخطط بين المراجع غير متطابقين

**الدليل:** مرجع Backend يثبت 32 جدولًا، بينما ملف قاعدة البيانات يسرد 36 جدولًا على أنها إلزامية. لكن الجدول رقم 36، ai_decision_outcomes، موصوف بأنه «اختياري لاحقًا»، كما تصفه مهمة DB-043 بأنها اختيارية. إذن عدد الجداول الإلزامية غير محسوم داخل مرجع قاعدة البيانات نفسه. الأرقام 37 إلى 39 هي جدول سجل AI الاختياري وجدولا CSV الاختياريان.

**الملفات المتأثرة:** backend.docx (D-07 وقائمة 32 جدولًا)، database final(1).docx (مقدمة المخطط والجدول 36 وDB-043)، backend/INTEGRATION_READINESS.md.

**التوصية:** اعتماد database final(1).docx مرجع قاعدة البيانات لهذه المطابقة، وتوثيق أن قائمة الـ32 القديمة قد استُبدلت أو إعداد mapping صريح لها. يحسم مالك قاعدة البيانات هل ai_decision_outcomes إلزامي؛ ثم تُحدّث وثيقة الجاهزية لتذكر القائمة والأسماء المعتمدة. لا يمكن اعتبار فرق العدد وحده mapping.

**قرار الفريق:** اعتماد mapping بين عقد Backend القديم والمخطط المحدد، وتثبيت إلزامية الجدول 36. اعتماد الملف المحدد نفسه محسوم بتوجيه المهمة ولا يحتاج إلى إعادة إثبات.

### F-02 — مساحة أكواد المنتجات والمتغيرات متعارضة

**الدليل:** قرار Backend D-01 يطلب مساحتي أسماء منفصلتين لـproduct_code وSKU. قرار قاعدة البيانات DEC-04 يطلب سجل أكواد واحدًا على مستوى النشاط يمنع التصادم بين المنتج والمتغير. قواعد backend/product_rules.py وbackend/variant_rules.py تستخدم سجلًا مشتركًا وتمنع حاليًا التصادم بين النوعين؛ أي إن الشيفرة الحالية تتبع DEC-04 وتخالف D-01.

**الملفات المتأثرة:** backend.docx (D-01)، database final(1).docx (DEC-04، الجدول 09 وDB-013)، backend/product_rules.py، backend/variant_rules.py، واختبارات قواعد المنتج والمتغير.

**التوصية:** بما أن ملف قاعدة البيانات المحدد هو مرجع DB المعتمد، أوصي باعتماد المساحة الموحدة وتسجيل D-01 بوصفه قرارًا مستبدلًا. إذا قرر مالك المنتج فصل الأكواد، فيلزم تعديل DEC-04 وقيد السجل قبل إنشاء المخطط؛ لا ينبغي أن يبقى التنفيذ والوثيقتان على سياسات مختلفة.

**قرار الفريق:** موافقة مالك المنتج وBackend وDatabase على مساحة الأسماء النهائية.

### F-03 — تمثيل أرصدة المخزون يختلف، مع اتفاق على ما يمكن بيعه

**الدليل:** قرار Backend D-02 يسمي الرصيد branch_inventory.available_qty ويقول إن كميات النقل والفحص والتالف تُتبع من الأحداث. المخطط المحدد يسميه inventory_balances ويخزن available_qty وinspection_qty وdamaged_qty، بينما يحتفظ بكمية النقل في stock_transfer_items ويسجل التغييرات في inventory_movements. قواعد backend/stock_rules.py تقرأ available_qty فقط وتتجاهل عمدًا النقل والفحص والتالف؛ لذا تتفق قاعدة البيع، لكن مصدر الحقيقة وشكل التخزين مختلفان.

**الملفات المتأثرة:** backend.docx (D-02)، database final(1).docx (الجداول 10 و11 و24، DEC-08، القسم 6.1)، backend/stock_rules.py، backend/inventory_movement_rules.py، backend/INTEGRATION_READINESS.md.

**التوصية:** تحديد ما إذا كانت أرصدة الفحص والتالف في inventory_balances أرصدة حالية مادية تُصالح مع السجل، أم تجميعات مشتقة من inventory_movements. توثيق mapping الاسم branch_inventory إلى inventory_balances وproduct_variant_id إلى variant_id. يبقى المتاح وحده قابلًا للبيع، وتبقى كمية النقل خارج رصيد الفرع المتاح.

**قرار الفريق:** اعتماد نموذج مصدر الحقيقة ومصالحة الأرصدة مع ledger قبل تنفيذ الاستعلامات والكتابة.

### F-04 — دقة العملة والمبالغ لا تتطابق

**الدليل:** قرار Backend D-05 يحدد JOD وسعر الوحدة DECIMAL(14,3) والإجمالي DECIMAL(16,3). قرار قاعدة البيانات DEC-02 يحدد المال DECIMAL(14,2)، وتستخدم بنود البيع DECIMAL(14,2) مع تقريب line_total إلى منزلتين. قواعد backend/product_rules.py وbackend/sale_rules.py تقبل ثلاث منازل وتفرض حاليًا حدود DECIMAL(12,3)؛ لذلك توجد فروق في المقياس والمدى والتقريب. كما لا يحدد ملف قاعدة البيانات العملة صراحة.

**الملفات المتأثرة:** backend.docx (D-05)، database final(1).docx (DEC-02 والجداول 07 و08 و16 وقواعد المبالغ)، backend/product_rules.py، backend/variant_rules.py، backend/sale_rules.py، backend/sales_history_rules.py، واختباراتها.

**التوصية:** اعتماد قرار مالي واحد يحدد العملة، دقة سعر الوحدة والإجمالي، المدى، ومتى يتم التقريب. وباعتبار ملف قاعدة البيانات هو المخطط المعتمد، أوصي بأن يثبت مالك المنتج/المالية العملة ثم يُستبدل D-05 رسميًا وتُواءم قواعد Backend مع DECIMAL(14,2) إذا كانت منزلتان كافيتين. إذا كانت دقة JOD بثلاث منازل متطلبًا، فيجب تحديث DEC-02 وكل أعمدة البيع والتقريب قبل أي migration.

**قرار الفريق:** موافقة Product/Finance وBackend وDatabase؛ لا يمكن حسم ذلك بمجرد تحويل القيم بين الأنواع.

### F-05 — عقد المعاملة وقواعد الإلغاء يخالفان D-03 وDEC-09

**الدليل:** قرار Backend D-03 وقرار قاعدة البيانات DEC-09 متفقان: الكمية المعادة عند الإلغاء هي المباعة ناقص الكميات التي أُعيدت بالفعل، مع منع مرتجعات جديدة بعد الإلغاء. لكن backend/TRANSACTION_SAFETY_CONTRACT.md وقواعد backend/sale_cancellation_rules.py يرفضان الطلب والموافقة عند وجود مرتجع معالج، وcalculate_restoration_quantities يعيد كامل كميات البيع عند عدم وجود ذلك الشرط. هذا تعارض في عقد المعاملات والتنفيذ مع D-03 وDEC-09، وليس خلافًا بين قراري Backend وDatabase.

**الملفات المتأثرة:** backend/sale_cancellation_rules.py، backend/inventory_movement_rules.py، backend/TRANSACTION_SAFETY_CONTRACT.md، backend/tests/test_sale_cancellation_rules.py، backend/tests/test_inventory_movement_rules.py، database final(1).docx (DEC-09 وPROC-07 وDB-026).

**التوصية:** عند تنفيذ التخزين، احتساب صافي الكمية لكل بند تحت الأقفال، وإلغاء البيع وحركة المخزون وطلب الإلغاء ذريًا، ومنع أي مرتجع لاحق بعد CANCELLED. لا يلزم قرار منتج إضافي ما لم تتغير قاعدة BW-24.

**قرار الفريق:** لا؛ المطلوب تنفيذ العقد المعتمد. اعتماد التغيير الوظيفي مطلوب فقط إذا أراد الفريق رفض الإلغاء بعد أي مرتجع.

### F-06 — إكمال التحويل مع فرق مفتوح متعارض وغامض داخل مرجع قاعدة البيانات

**الدليل:** قرار Backend D-04 يمنع COMPLETED قبل أن تصبح الكمية غير المحسومة صفرًا. قرار قاعدة البيانات DEC-07 يقول إن النقص يبقى قيد النقل حتى تسويته أو شطبه المعتمد، مع تعريف COMPLETED بأنه تأكيد الاستلام. لكن PROC-12 وجدول انتقال الحالات يسمحان بتعيين رأس التحويل COMPLETED بعد استلام جزئي مع بقاء in_transit_qty. قواعد backend/transfer_rules.py تسمح أيضًا بالإكمال مع فرق مفتوح؛ فهي تتبع إجراء PROC-12 لا D-04. يمكن التوفيق فقط إذا فُصلت حالة رأس التحويل عن عهدة الكمية، وهذا الفصل غير مصاغ بوضوح كافٍ.

**الملفات المتأثرة:** backend.docx (D-04 وBE-36)، database final(1).docx (DEC-07، الجداول 23–26، PROC-12 إلى PROC-14، القسم 6.1)، backend/transfer_rules.py، backend/inventory_movement_rules.py، backend/TRANSACTION_SAFETY_CONTRACT.md واختبارات التحويل.

**التوصية:** أوصي باتباع إجراء قاعدة البيانات المفصل: يجوز أن يعني COMPLETED اكتمال تأكيد الاستلام، بينما تبقى الكمية الناقصة في in_transit_qty وسجل discrepancy إلى التسوية. يجب تعديل D-04 وتوضيح DEC-07 وتعريف الحالة في العقد قبل التكامل. إذا كان معنى COMPLETED لدى الفريق هو إغلاق كل العهدة، فيجب عكس الاختيار وتعديل PROC-12 وقواعد Backend.

**قرار الفريق:** موافقة مالك قصة التحويل وBackend وDatabase على معنى الحالة، والتوفيق بين DEC-07 وPROC-12 وD-04.

### F-07 — عقد idempotency في Backend أوسع من المخطط

**الدليل:** قرار Backend D-06 وBE-52 يطلبان مفتاحًا فريدًا بحسب النشاط ونوع العملية والمفتاح، وpayload_hash، وحالة التنفيذ، وإعادة النتيجة المحفوظة، ويذكر BE-52 جدول idempotency_requests. المخطط المحدد يستخدم مفاتيح خاصة بكل نوع مستند (مثل request_key في البيع والاستلام والتحويل والمرتجع)، وoperation_key في ledger وclient_operation_key لقرار AI، ولا يعرّف جدولًا عامًا أو حقول payload_hash ونتيجة الاستجابة. قواعد backend/transaction_safety_rules.py تحسب البصمة وتقرر replay/conflict فقط؛ ولا تحفظ الحالة أو النتيجة.

**الملفات المتأثرة:** backend.docx (D-06 وBE-52)، database final(1).docx (الجداول 11 و15 و21 و23 و27 و35، القسم 9)، backend/transaction_safety_rules.py، backend/TRANSACTION_SAFETY_CONTRACT.md.

**التوصية:** اعتماد نموذج واحد يضمن ذريًا التفرد، رفض إعادة استخدام المفتاح بحمولة مختلفة، ومنع الأثر المكرر وإعادة نتيجة النجاح. إما إضافة مخزن idempotency عام إلى المخطط وعقد المعاملات، أو اعتماد مفاتيح المستندات الحالية رسميًا مع إضافة البيانات والسلوك اللازمين لمطابقة D-06/BE-52 ثم تحديث عقد Backend. لا يكفي وجود مفتاح فريد في ledger لإعادة نتيجة API.

**قرار الفريق:** موافقة Backend وDatabase على مكان حفظ المفتاح والبصمة والحالة والنتيجة وحدود المعاملة.

### F-08 — WAIT في عقد توصية AI غير قابل للحفظ وفق ENUM الحالي

**الدليل:** مهمة Backend BE-41 تسمح بتوصية PURCHASE أو TRANSFER أو WAIT. حقل recommendation_type في الجدول 33 من مرجع قاعدة البيانات هو ENUM يقتصر على PURCHASE وTRANSFER. لا توجد حاليًا خدمة AI موصولة بهذا المخطط في Backend.

**الملفات المتأثرة:** backend.docx (BE-41)، database final(1).docx (الجدول 33 وDB-041)، وأي عقد API/خدمة AI لاحقة.

**التوصية:** أوصي بأن تكون WAIT استجابة API أو حالة عدم إصدار توصية، لا صفًا في ai_recommendations؛ يوثّق ذلك مع واجهة العميل. إذا كان لا بد من حفظها كتوصية، يضاف القرار إلى ENUM وتعريفات السلوك.

**قرار الفريق:** موافقة مالك المنتج/AI وBackend وDatabase على دلالة WAIT ومكان تمثيلها.

### F-09 — سجل الجلسة لا يعرّف تخزين بصمة CSRF المطلوبة

**الدليل:** جدول auth_sessions في قاعدة البيانات يحوي بصمة رمز الجلسة، ونسخة الصلاحية وقت الدخول، والانتهاء والإبطال، لكنه لا يعرض حقلًا لبصمة CSRF. backend/session_auth.py يتطلب حفظ csrf_token_digest في سجل الجلسة. يمكن مواءمة auth_version مع users.access_version وaccess_version_at_login، ومواءمة SessionStore.delete مع تحديث revoked_at، لكن بصمة CSRF تحتاج تخزينًا معتمدًا.

**الملفات المتأثرة:** database final(1).docx (الجداول 03–04 وDB-008)، backend/session_auth.py، backend/SESSION_AUTH_FOUNDATION.md، backend/routes/auth.py.

**التوصية:** إضافة حقل digest إلى auth_sessions أو اعتماد مخزن جلسات يضمن تخزينه وربطه بجلسة الخادم. توثيق تحويل SHA-256 من التمثيل السداسي في Backend إلى BINARY(32) في المخطط، وربط الحذف المنطقي بـrevoked_at. لا تقبل بصمة CSRF من العميل كمصدر موثوق.

**قرار الفريق:** موافقة Database وBackend/الأمن على موضع التخزين وmapping حقول نسخة الصلاحية والإبطال.

### F-10 — خوارزمية تجزئة كلمة المرور في التطبيق لا تطابق الخوارزميات المذكورة في المخطط

**الدليل:** يطلب حقل users.password_hash في قاعدة البيانات Argon2id أو bcrypt عبر Backend. backend/security.py يستدعي werkzeug.security.generate_password_hash دون تحديد خوارزمية؛ والنسخة المثبتة محليًا Werkzeug 3.1.9 تستخدم scrypt افتراضيًا. لا تظهر حزمة Argon2 أو bcrypt في backend/requirements.txt. طول العمود لا يمنع التخزين، لكن سياسة الخوارزمية مختلفة.

**الملفات المتأثرة:** database final(1).docx (الجدول 03)، backend/security.py، backend/requirements.txt، backend/tests/test_security.py.

**التوصية:** اعتماد خوارزمية صريحة قبل تفعيل تسجيل الحسابات: إما مواءمة Backend مع Argon2id/bcrypt كما ينص المخطط، أو تعديل قرار قاعدة البيانات ليجيز scrypt وإثبات سياسة الترقية والتحقق من hashes القديمة. لا تعتمد اختيار الخوارزمية على القيمة الافتراضية لمكتبة.

**قرار الفريق:** موافقة مسؤول الأمن وBackend وDatabase على الخوارزمية وسياسة ترقية كلمات المرور.

## 3. توافقات تحتاج mapping ولا تمثل خلافًا وظيفيًا بحد ذاتها

أسماء API والحقول الداخلية مختلفة، ويمكن ربطها في طبقة الخدمة دون تغيير سلوك المنتج: owner_name إلى users.full_name، وbusiness_name إلى businesses.name، واسم مستخدم API إلى full_name، وcode إلى variant_code، وproduct_variant_id إلى variant_id. كما يلزم تحويل قيم الدور المعروضة إلى ENUM المخطط، وربط CatalogCodeEntry(resource_type, resource_id) بسجل catalog_code_registry ذي product_id أو variant_id. لا توجد في المستودع طبقة persistence لتنفيذ هذه التحويلات بعد.

الملفات المتأثرة مستقبلًا: API_CONTRACT.md، backend/routes/auth.py، backend/routes/users.py، قواعد المنتجات والمتغيرات، وعقد واجهة قاعدة البيانات.

## 4. حالة الجاهزية التنفيذية

- backend/db.py يفتح اتصالًا مباشرًا بـmysql.connector فقط؛ لا يوجد تنفيذ لاستعلامات أو معاملات الأعمال أو ORM أو repositories أو migrations أو DDL.
- قرار Backend D-07 يحدد SQLAlchemy/Flask-Migrate وسلسلة Alembic واحدة. هذه المسؤولية متوافقة مع طلب ملف قاعدة البيانات لتسليم migrations، لكنها غير مطبقة في المشروع: SQLAlchemy وAlembic/Flask-Migrate غير موجودة في الاعتماديات أو الملفات الحالية. يلزم تنفيذ القرار في مسار واحد ومراجعته مع Database، لا إنشاء مخططين متوازيين.
- مسارات API الأساسية الصحيحة ما زالت تعيد 501، ولا يوجد تكامل قراءة/كتابة مع MySQL. لذلك البنود أعلاه تدقيق عقود وقواعد فقط؛ لا تثبت توافقًا تشغيليًا.
- backend/INTEGRATION_READINESS.md يحتاج تحديثًا لاحقًا ليعكس مصدر الجداول المحدد وعددها وأسماء المخطط الفعلية. لم يُعدّل ضمن هذا العمل.
- قواعد Backend واختباراتها وحدات نقية/معزولة؛ لم تُشغّل اختبارات في هذا التدقيق بناءً على نطاق العمل.

## 5. قرارات موافقة الفريق المطلوبة

## التوصية قبل بدء التكامل الدائم

احسم القرارات أعلاه وسجّلها في عقد Backend–Database واحد. بعد ذلك حدّث وثائق الجاهزية والعقد، ثم نفّذ schema/migrations في السلسلة المعتمدة وابدأ بمسار هوية وجلسة رأسي قبل بقية عمليات المخزون. حتى ذلك الحين، لا يُعد وجود موصل MySQL أو قواعد Python إثباتًا لتكامل قاعدة البيانات.
